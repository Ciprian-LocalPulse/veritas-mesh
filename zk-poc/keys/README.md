# `zk-poc/keys/` — Checked-in Groth16 Keys (small circuits only)

**These are NON-CEREMONY, fixed-seed keys. Read this entire file before
using them for anything beyond local development or testing.**

## What's here and why

`banking-basel-iii.{pk,vk}` and `healthcare-hipaa.{pk,vk}` — the two
circuits whose proving keys are small enough (29,296 and 12,560 bytes
respectively) to check into git without meaningfully affecting repo size.
Generated by `cargo run --package veritas-zk-poc --release --bin
generate_keys -- <dir>` with the tool's fixed seed (`42`) — see that
tool's own module doc comment (`src/bin/generate_keys.rs`) for the full
reasoning behind this whole approach.

**`banking-basel-iii-bound.{pk,vk}` (~16.4 MiB) and
`gov-supply-chain-integrity.{pk,vk}` (~64 MiB) are deliberately NOT
here.** Checking multi-megabyte binaries into a git repo that's cloned
frequently is poor practice on its own, and doubly unjustified for keys
nobody should trust yet anyway (see below) — generate them locally with
the same tool if you need them:

```
cargo run --package veritas-zk-poc --release --bin generate_keys -- /some/local/dir
```

## Manifest (regenerate and diff against this if you don't trust it)

```
banking-basel-iii    groth16-bn254   pk=29296 bytes  vk=296 bytes
  circuit_digest = 979f2465a292dc8ab1dd233b46cfe2144f4a1e542aeb0a2cdff72fa8fd915912

healthcare-hipaa      groth16-bn254   pk=12560 bytes  vk=328 bytes
  circuit_digest = 8ad2e4b079f12a1c8fbc796d9e3d5edb6ffe2695ad1d486c3c105f8a1a3e8f95
```

`circuit_digest` is `SHA-256(verifying_key_bytes)`, matching
[`proto/veritas/v1/rule_module.proto`](../../proto/veritas/v1/rule_module.proto)'s
`RuleModuleManifest.circuit_digest` field exactly — computable directly
via `veritas_zk_poc::Keys::verifying_key_digest()`. If you load these
files and get a different digest, something is wrong (a different
`arkworks`/`ark-bn254` version producing non-byte-identical
serialization, a corrupted download, etc.) — don't proceed as if nothing
happened.

## Why "checked in" is not "trustworthy"

Every key here comes from `zk-poc/`'s own `setup`/`setup_healthcare`
functions, which use a `ChaCha20Rng` seeded from a plain `u64` — the
"toxic waste" of a real Groth16 trusted setup (the randomness used during
key generation, which MUST be destroyed for the setup to be secure) is,
here, just the number 42, reproducible by anyone who reads this file.
**Reproducing these exact files is a feature for this repo's own testing
purposes (byte-identical keys across CI runs, reviewers, and contributors
— see `generate_keys.rs`'s own doc comment for why that's deliberate) and
simultaneously the reason these keys must never be trusted for a real
attestation anyone relies on.** A real deployment needs one of:

1. A genuine multi-party computation (MPC) ceremony, where no single
   participant knows the full toxic waste (the standard approach for
   Groth16's per-circuit setup — see
   [RFC 0002](../../rfcs/0002-proof-system-selection.md)'s own notes on
   this being an ongoing operational cost of choosing Groth16 over a
   transparent-setup system).
2. Migrating the relevant rule module to the STARK track
   RFC 0002 also describes, which needs no trusted setup at all.

Neither exists yet for any rule module in this repository. Loading these
files with [`Keys::load_from_files`](../src/lib.rs) will work exactly as
described — that a function works is not a claim about what it's safe to
use for.

## Loading these in code

```rust
use std::path::Path;
use veritas_zk_poc::Keys;

let keys = Keys::load_from_files(
    Path::new("zk-poc/keys/healthcare-hipaa.pk"),
    Path::new("zk-poc/keys/healthcare-hipaa.vk"),
)?;

// Recommended: verify you loaded the key you meant to.
let digest = keys.verifying_key_digest()?;
assert_eq!(hex::encode(digest), "8ad2e4b079f12a1c8fbc796d9e3d5edb6ffe2695ad1d486c3c105f8a1a3e8f95");
```

`core::proof::groth16_bn254`'s backend structs (`BankingGroth16Backend`,
`HealthcareGroth16Backend`, etc.) all expose `from_keys(keys: Keys)`
specifically so a caller can load once, this way, at startup — instead of
calling that backend's `setup()` (which regenerates fresh, different,
equally-untrustworthy keys every time) per attestation. No code in this
repository does that loading automatically yet; wiring `core::attest`'s
functions to load from here (or somewhere real, once a real ceremony
exists) instead of calling `setup()` directly remains open — see
`zk-poc/README.md` item 3's updated status.
